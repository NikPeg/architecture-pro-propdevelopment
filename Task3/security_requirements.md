# Требования к безопасности внешних интеграций "Умный дом"

## Версия документа: 1.0
## Дата: Ноябрь 2025

---

## 1. ВВЕДЕНИЕ

### 1.1. Цель документа

Данный документ определяет требования к безопасности для интеграции систем PropDevelopment с внешней платформой партнера для предоставления сервисов "Умный дом":
- Интеллектуальный домофон с биометрией
- Интеллектуальный шлагбаум с распознаванием номеров

### 1.2. Область применения

Требования распространяются на:
- Платформу партнера Smart Home Services
- Новый микросервис smart-home-integration-service
- API Gateway для внешних интеграций
- Мобильное приложение для собственников (обновленное)
- Все каналы передачи данных между системами

### 1.3. Нормативные ссылки

- **ФЗ-152** "О персональных данных" (особые требования к биометрическим данным)
- **ФЗ-149** "Об информации, информационных технологиях и о защите информации"
- **Приказ ФСТЭК России №31** от 14.03.2014
- **ISO/IEC 27001:2013** - Системы менеджмента информационной безопасности
- **ISO/IEC 27002:2022** - Практические правила управления информационной безопасностью
- **OWASP API Security Top 10 2023**
- **ГОСТ Р 52633.5-2011** - Защита информации (биометрия)

### 1.4. Критичность данных

**Особая категория персональных данных** (согласно ФЗ-152 ч.1 ст.11):
- 🔴 Биометрические данные (шаблоны лиц)
- 🔴 Видеозаписи с изображениями лиц
- 🔴 Данные о перемещениях (время входа/выхода)
- 🔴 Номера автомобилей

**Конфиденциальные данные:**
- 🟠 Привязка квартиры к собственнику
- 🟠 Временные коды доступа для гостей
- 🟠 Права доступа жильцов

## 2. АРХИТЕКТУРНЫЕ ТРЕБОВАНИЯ БЕЗОПАСНОСТИ

### 2.1. Общие принципы

#### 2.1.1. Defense in Depth (Эшелонированная защита)

**Требование SEC-ARCH-001**: Система ДОЛЖНА реализовывать многоуровневую защиту:

1. **Периметр**: Firewall + WAF
2. **Шлюз**: API Gateway с аутентификацией и авторизацией
3. **Приложение**: Проверка прав на уровне smart-home-integration-service
4. **Данные**: Шифрование биометрических данных в БД

**Критерий соответствия**: Компрометация одного уровня НЕ ДОЛЖНА приводить к компрометации всей системы.

#### 2.1.2. Zero Trust Architecture

**Требование SEC-ARCH-002**: Система ДОЛЖНА следовать принципу "Never Trust, Always Verify":

- Каждый запрос ДОЛЖЕН проходить аутентификацию и авторизацию
- Доверие НЕ ДОЛЖНО основываться только на сетевом расположении
- Минимальные привилегии для каждого компонента

#### 2.1.3. Least Privilege (Минимальные привилегии)

**Требование SEC-ARCH-003**: 
- Платформа партнера ДОЛЖНА иметь доступ ТОЛЬКО к необходимым данным
- Собственник ДОЛЖЕН управлять ТОЛЬКО своими устройствами
- Жилец ДОЛЖЕН иметь доступ ТОЛЬКО к разрешенным зонам

#### 2.1.4. Data Minimization (Минимизация данных)

**Требование SEC-ARCH-004**:
- НЕ ПЕРЕДАВАТЬ платформе партнера больше данных, чем необходимо
- Использовать UUID вместо ФИО в API
- НЕ ХРАНИТЬ исходные биометрические данные, только хеши/шаблоны

### 2.2. API Gateway (Критический компонент)

#### 2.2.1. Обязательность API Gateway

**Требование SEC-GW-001**: ВСЕ взаимодействия с внешней платформой партнера ДОЛЖНЫ проходить через централизованный API Gateway.

**Обоснование**: Устранение проблемы "отсутствия системного контроля за API партнеров" (из Task2).

**Функции API Gateway:**
1. ✅ Аутентификация запросов (OAuth 2.0)
2. ✅ Авторизация на основе контрактов API
3. ✅ Rate Limiting (защита от DDoS и злоупотребления)
4. ✅ Валидация входных данных (JSON Schema)
5. ✅ Логирование всех запросов и ответов
6. ✅ Шифрование трафика (TLS 1.3)
7. ✅ Мониторинг и алертинг аномалий

#### 2.2.2. Технологический стек

**Требование SEC-GW-002**: Использовать одно из проверенных решений:
- Kong Gateway (рекомендуется для Kubernetes)
- Apigee (Google Cloud)
- AWS API Gateway (если используется AWS)
- Azure API Management (если используется Azure)

#### 2.2.3. Rate Limiting

**Требование SEC-GW-003**: API Gateway ДОЛЖЕН ограничивать частоту запросов:

| Endpoint | Лимит | Окно |
|----------|-------|------|
| Открытие двери/шлагбаума | 10 req/min на пользователя | Sliding window |
| Получение журнала событий | 30 req/min на пользователя | Sliding window |
| Настройка правил доступа | 20 req/hour на пользователя | Fixed window |
| Платформа партнера → PropDevelopment | 1000 req/min | Sliding window |
| PropDevelopment → Платформа партнера | 500 req/min | Sliding window |

**Критерий соответствия**: При превышении лимита возвращать HTTP 429 (Too Many Requests) с заголовком Retry-After.

### 2.3. Микросервисная архитектура

#### 2.3.1. Изолированный микросервис

**Требование SEC-ARCH-005**: Интеграция с платформой партнера ДОЛЖНА быть реализована в отдельном микросервисе `smart-home-integration-service`.

**Обоснование**: 
- Изоляция рисков (компрометация не затронет другие сервисы)
- Независимое масштабирование
- Упрощенный аудит и мониторинг

#### 2.3.2. Отдельная база данных

**Требование SEC-ARCH-006**: Данные "Умного дома" ДОЛЖНЫ храниться в отдельной БД `smart-home-db`.

**Структура данных:**
```sql
-- Устройства
devices (device_id, device_type, location, apartment_id, status)

-- Правила доступа
access_rules (rule_id, device_id, user_id, access_type, valid_from, valid_until)

-- Биометрические шаблоны (НЕ исходные данные!)
biometric_templates (template_id, user_id, template_hash, algorithm, created_at)

-- Журнал событий (immutable)
access_log (event_id, device_id, user_id, timestamp, action, result, metadata)

-- Гостевые доступы
guest_access (guest_id, host_id, device_id, access_code, valid_from, valid_until)
```

**Критерий соответствия**: Никакие другие сервисы НЕ ДОЛЖНЫ иметь прямой доступ к этой БД.

## 3. АУТЕНТИФИКАЦИЯ И АВТОРИЗАЦИЯ

### 3.1. Протоколы аутентификации

#### 3.1.1. OAuth 2.0 для API интеграций

**Требование SEC-AUTH-001**: Взаимодействие между PropDevelopment и платформой партнера ДОЛЖНО использовать **OAuth 2.0**.

**Выбранный flow**: **Client Credentials Grant** (machine-to-machine)

**Обоснование**: 
- Стандартизированный протокол
- Поддержка токенов с ограниченным временем жизни
- Возможность отзыва доступа
- Разграничение прав через scopes

**Схема взаимодействия:**

```
PropDevelopment                    Partner Platform
    |                                     |
    |  1. POST /oauth/token              |
    |     client_id=propdevelopment      |
    |     client_secret=***              |
    |     grant_type=client_credentials  |
    |     scope=devices:read,            |
    |           devices:control,         |
    |           events:read              |
    | ----------------------------------> |
    |                                     |
    |  2. Response:                      |
    |     access_token=eyJ...            |
    |     token_type=Bearer              |
    |     expires_in=3600                |
    | <---------------------------------- |
    |                                     |
    |  3. API Request                    |
    |     Authorization: Bearer eyJ...   |
    | ----------------------------------> |
```

**Требования к токенам:**
- **Access token TTL**: 1 час (короткий срок для снижения рисков)
- **Refresh token**: НЕ используется (Client Credentials)
- **Token storage**: Безопасное хранилище (HashiCorp Vault, AWS Secrets Manager)
- **Token rotation**: Автоматическое обновление за 5 минут до истечения

#### 3.1.2. Mutual TLS (mTLS)

**Требование SEC-AUTH-002**: Дополнительно к OAuth 2.0 ДОЛЖНА использоваться взаимная TLS аутентификация (mTLS).

**Обоснование**: Defense in Depth - двойная аутентификация (токен + сертификат).

**Требования:**
- ✅ Клиентский сертификат от PropDevelopment
- ✅ Серверный сертификат от платформы партнера
- ✅ Проверка Certificate Pinning в API Gateway
- ✅ Срок действия сертификатов: 1 год
- ✅ Автоматическая ротация за 30 дней до истечения

#### 3.1.3. API Keys для внутренних сервисов

**Требование SEC-AUTH-003**: Взаимодействие между внутренними сервисами PropDevelopment ДОЛЖНО использовать API Keys + mTLS.

**Внутренние интеграции:**
- `tenant-mobile-app` → `smart-home-integration-service`: JWT (OAuth 2.0 от auth-service-1)
- `smart-home-integration-service` → `tenant-core-app`: mTLS + service account
- `smart-home-integration-service` → `CRM`: mTLS + service account

### 3.2. Авторизация

#### 3.2.1. Role-Based Access Control (RBAC)

**Требование SEC-AUTHZ-001**: Система ДОЛЖНА реализовывать RBAC со следующими ролями:

| Роль | Права доступа | Область действия |
|------|---------------|------------------|
| **owner** (Собственник) | - Полное управление устройствами в своей квартире<br>- Создание гостевых доступов<br>- Просмотр полного журнала<br>- Управление биометрией | Собственная квартира + общие зоны дома |
| **resident** (Жилец/Арендатор) | - Использование устройств<br>- Просмотр своего журнала<br>- Добавление своей биометрии (с согласия owner) | Арендуемая квартира + разрешенные зоны |
| **guest** (Гость) | - Временный доступ по коду/ссылке<br>- Открытие двери по видеозвонку | Только на время действия приглашения |
| **security** (Охрана/УК) | - Мониторинг всех событий<br>- Экстренное открытие<br>- Просмотр журнала всего дома | Весь жилой комплекс |
| **service_account** (Сервисная учетка) | - Техническое взаимодействие между сервисами | По назначению |

#### 3.2.2. Attribute-Based Access Control (ABAC)

**Требование SEC-AUTHZ-002**: Дополнительно к RBAC применять ABAC для тонкой настройки:

**Атрибуты для проверки:**
- `user.apartment_id` == `device.apartment_id` (устройства только своей квартиры)
- `current_time` BETWEEN `access_rule.valid_from` AND `access_rule.valid_until` (временные ограничения)
- `device.status` == `active` (только активные устройства)
- `user.biometric_consent` == `true` (согласие на биометрию)

**Пример политики:**
```json
{
  "policy_id": "allow_door_open",
  "effect": "allow",
  "actions": ["device:open_door"],
  "conditions": {
    "and": [
      {"user.role": {"in": ["owner", "resident"]}},
      {"user.apartment_id": {"equals": "device.apartment_id"}},
      {"current_time": {"between": ["access_rule.valid_from", "access_rule.valid_until"]}},
      {"device.status": {"equals": "active"}}
    ]
  }
}
```

#### 3.2.3. Область действия OAuth scopes

**Требование SEC-AUTHZ-003**: Платформа партнера ДОЛЖНА получать минимальный набор прав (scopes):

| Scope | Описание | Обоснование необходимости |
|-------|----------|---------------------------|
| `devices:read` | Чтение списка устройств и их статуса | Для отображения в интерфейсе партнера |
| `devices:control` | Управление устройствами (открыть/закрыть) | Основная функциональность |
| `events:write` | Отправка событий в PropDevelopment | Логирование действий (кто, когда открыл) |
| `biometry:verify` | Проверка биометрического шаблона | Для распознавания лиц |

**НЕ ПРЕДОСТАВЛЯТЬ:**
- ❌ `users:read` - партнер НЕ должен видеть персональные данные
- ❌ `biometry:read` - партнер НЕ должен читать биометрические шаблоны
- ❌ `devices:delete` - партнер НЕ должен удалять устройства

## 4. ЗАЩИТА ДАННЫХ

### 4.1. Шифрование при передаче

#### 4.1.1. TLS 1.3

**Требование SEC-DATA-001**: ВСЕ коммуникации ДОЛЖНЫ использовать **TLS 1.3** (или минимум TLS 1.2).

**Запрещенные протоколы:**
- ❌ SSL 2.0, SSL 3.0
- ❌ TLS 1.0, TLS 1.1

**Разрешенные cipher suites (TLS 1.3):**
- ✅ TLS_AES_256_GCM_SHA384
- ✅ TLS_CHACHA20_POLY1305_SHA256
- ✅ TLS_AES_128_GCM_SHA256

**Проверка:** Регулярное сканирование с помощью SSLLabs или testssl.sh.

#### 4.1.2. Certificate Pinning для мобильного приложения

**Требование SEC-DATA-002**: Мобильное приложение ДОЛЖНО использовать Certificate Pinning для защиты от MITM атак.

**Реализация:**
- Встраивание публичного ключа сертификата в приложение
- Проверка при каждом HTTPS подключении
- Backup pins для плавной ротации сертификатов

**Пример (iOS):**
```swift
let publicKeyHash = "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA="
let pinningManager = PinningManager(pinnedHashes: [publicKeyHash])
```

### 4.2. Шифрование при хранении

#### 4.2.1. Биометрические данные

**Требование SEC-DATA-003**: Биометрические данные ДОЛЖНЫ обрабатываться со следующими мерами защиты:

1. **НЕ ХРАНИТЬ** исходные изображения лиц в PropDevelopment
2. **ХРАНИТЬ** только биометрические шаблоны (хеши)
3. Шаблоны ДОЛЖНЫ быть **зашифрованы** с использованием AES-256
4. Ключи шифрования ДОЛЖНЫ храниться в **Hardware Security Module (HSM)** или Key Management Service
5. Каждый шаблон ДОЛЖЕН быть засолен (salt) уникальным значением

**Схема:**
```
Исходное фото лица (на устройстве партнера)
    ↓
Извлечение биометрического шаблона (128-512 байт)
    ↓
Хеширование: SHA-256(template || salt)
    ↓
Шифрование: AES-256-GCM(hash, key_from_HSM)
    ↓
Хранение в smart-home-db
```

**Критерий соответствия:** Невозможно восстановить исходное изображение из хранимых данных.

#### 4.2.2. Согласие на обработку биометрии

**Требование SEC-DATA-004**: Перед сбором биометрических данных ДОЛЖНО быть получено **письменное согласие** пользователя (ФЗ-152 ч.1 ст.11).

**Процесс:**
1. Пользователь инициирует добавление биометрии в приложении
2. Отображается полный текст согласия с пояснениями
3. Пользователь подтверждает галочкой и нажимает "Согласен"
4. Согласие записывается в БД с timestamp и IP адресом
5. Пользователь получает email-подтверждение

**Обязательная информация в согласии:**
- Цель обработки биометрии
- Кто обрабатывает данные (PropDevelopment + партнер)
- Срок хранения данных
- Права субъекта (отозвать согласие, удалить данные)
- Меры защиты

#### 4.2.3. Encryption at Rest для БД

**Требование SEC-DATA-005**: База данных `smart-home-db` ДОЛЖНА использовать Transparent Data Encryption (TDE).

**Технологии:**
- PostgreSQL: pgcrypto или встроенный TDE (для Enterprise)
- MySQL: InnoDB encryption
- AWS RDS: Encryption at rest
- Azure SQL: Transparent Data Encryption

**Критерий соответствия:** Даже при физическом доступе к дискам данные недоступны без ключей.

### 4.3. Классификация и обработка данных

#### 4.3.1. Data Loss Prevention (DLP)

**Требование SEC-DATA-006**: Система ДОЛЖНА предотвращать утечку чувствительных данных:

**Меры DLP:**
1. **API Response Filtering**: Биометрические данные НЕ ДОЛЖНЫ возвращаться в API ответах
2. **Логирование**: ПД НЕ ДОЛЖНЫ попадать в логи (маскирование)
3. **Мониторинг**: Алерты при попытках массового экспорта данных
4. **Database Activity Monitoring**: Аудит всех запросов к таблицам с ПД

**Пример маскирования в логах:**
```
❌ Плохо: "User Ivan Ivanov opened door at apartment 42"
✅ Хорошо: "User user_id=a7f3c2e opened door at apartment apartment_id=xyz"
```

#### 4.3.2. Минимизация данных в API

**Требование SEC-DATA-007**: API контракты с платформой партнера ДОЛЖНЫ содержать минимум персональных данных.

**Правила:**
- ✅ Использовать UUID вместо имен
- ✅ Передавать только необходимые поля
- ❌ НЕ передавать ФИО, адреса, телефоны
- ❌ НЕ передавать полные данные о квартире

**Пример API контракта:**

❌ **Плохой API (слишком много ПД):**
```json
{
  "user": {
    "full_name": "Иванов Иван Иванович",
    "phone": "+79001234567",
    "address": "г. Москва, ул. Ленина, д.1, кв.42",
    "passport": "1234 567890"
  },
  "action": "open_door"
}
```

✅ **Хороший API (минимум данных):**
```json
{
  "user_id": "a7f3c2e1-4b8f-4d3a-9e2c-1a7b8c9d0e1f",
  "device_id": "device_123",
  "action": "open_door",
  "timestamp": "2025-11-27T10:30:00Z"
}
```

### 4.4. Защита видеопотока

#### 4.4.1. Шифрование видео

**Требование SEC-DATA-008**: Видеопоток с домофона ДОЛЖЕН быть зашифрован.

**Технологии:**
- SRTP (Secure Real-time Transport Protocol) для live video
- HTTPS для video on demand
- End-to-end encryption между устройством и приложением

#### 4.4.2. Хранение видеозаписей

**Требование SEC-DATA-009**: Видеозаписи с изображениями лиц:
- ДОЛЖНЫ храниться не более **30 дней** (минимизация)
- ДОЛЖНЫ быть зашифрованы (AES-256)
- Доступ ТОЛЬКО для собственника и охраны
- Автоматическое удаление после истечения срока

## 5. ЛОГИРОВАНИЕ И МОНИТОРИНГ

### 5.1. Требования к логированию

#### 5.1.1. События для логирования

**Требование SEC-LOG-001**: ДОЛЖНЫ логироваться следующие события:

**Критические события безопасности:**
- ✅ Все попытки доступа (успешные и неуспешные)
- ✅ Открытие дверей и шлагбаумов
- ✅ Биометрическое распознавание (успех/отказ)
- ✅ Создание/изменение/удаление правил доступа
- ✅ Добавление/удаление биометрических шаблонов
- ✅ Создание гостевых доступов
- ✅ API вызовы к платформе партнера
- ✅ API вызовы от платформы партнера
- ✅ Ошибки аутентификации/авторизации
- ✅ Изменения конфигурации устройств
- ✅ Экстренные открытия охраной

**Формат лог-записи:**
```json
{
  "timestamp": "2025-11-27T10:30:00.123Z",
  "event_type": "door_opened",
  "severity": "info",
```

#### 5.1.2. Неизменяемость логов

**Требование SEC-LOG-002**: Логи событий доступа ДОЛЖНЫ быть **неизменяемыми** (immutable).

**Реализация:**
- Append-only таблица в БД
- Или использование специализированных решений: AWS CloudWatch Logs, Azure Monitor
- Или blockchain-подобная структура с хешированием

**Критерий соответствия:** Невозможно изменить или удалить записи без детектирования.

#### 5.1.3. Срок хранения логов

**Требование SEC-LOG-003**: 

| Тип логов | Срок хранения | Обоснование |
|-----------|---------------|-------------|
| События доступа | **1 год** | Требования ФЗ-152 для ПД |
| Биометрические события | **3 года** | Требования для особых категорий ПД |
| API вызовы | **6 месяцев** | Расследование инцидентов |
| Ошибки безопасности | **3 года** | Анализ паттернов атак |
| Аудит изменений | **5 лет** | Юридические требования |

#### 5.1.4. Централизованное логирование

**Требование SEC-LOG-004**: Все логи ДОЛЖНЫ отправляться в централизованную SIEM систему.

**Рекомендуемые решения:**
- ELK Stack (Elasticsearch, Logstash, Kibana)
- Splunk
- Wazuh
- Graylog

### 5.2. Мониторинг и алертинг

#### 5.2.1. Алерты безопасности

**Требование SEC-MON-001**: Система ДОЛЖНА генерировать алерты для следующих событий:

| Событие | Условие срабатывания | Severity | Получатели |
|---------|---------------------|----------|------------|
| Multiple failed access attempts | 5 неудачных попыток за 5 минут | 🔴 Critical | Security team, DevOps |
| Biometric spoofing attempt | Низкая уверенность распознавания (<0.5) | 🟠 High | Security team |
| API rate limit exceeded | Превышение лимита на 200% | 🟠 High | DevOps, API owner |
| Unauthorized API call | 401/403 от партнера | 🟡 Medium | DevOps |
| Mass data export | >100 записей за 1 запрос | 🔴 Critical | Security team, DBA |
| Device offline | Устройство не отвечает >5 минут | 🟡 Medium | Support team |
| Unusual access time | Доступ в нетипичное время (3-5 AM) | 🟡 Medium | Security team |
| Guest access expired | Попытка использовать истекший гостевой доступ | 🟢 Low | Audit log |

#### 5.2.2. Метрики для мониторинга

**Требование SEC-MON-002**: Система ДОЛЖНА собирать следующие метрики:

**Доступность:**
- Uptime API Gateway
- Uptime smart-home-integration-service
- Response time платформы партнера
- Количество успешных/неуспешных запросов

**Безопасность:**
- Количество успешных аутентификаций
- Количество неудачных аутентификаций
- Количество заблокированных запросов (rate limit)
- Количество биометрических распознаваний (успех/отказ)

**Бизнес-метрики:**
- Количество открытий дверей/шлагбаумов
- Количество активных гостевых доступов
- Среднее время отклика системы

#### 5.2.3. Anomaly Detection

**Требование SEC-MON-003**: Система ДОЛЖНА детектировать аномалии с использованием ML (в перспективе).

**Примеры аномалий:**
- Необычное время доступа для конкретного пользователя
- Необычная частота запросов
- Доступ из нетипичного местоположения (по IP)
- Массовые изменения правил доступа

## 6. ОРГАНИЗАЦИЯ ВЗАИМОДЕЙСТВИЯ СИСТЕМ

### 6.1. API Contract (Контракт API)

#### 6.1.1. OpenAPI спецификация

**Требование SEC-INT-001**: Все API ДОЛЖНЫ быть документированы в формате **OpenAPI 3.0** (Swagger).

**Обязательные секции:**
- Endpoints и методы
- Схемы данных (JSON Schema)
- Коды ответов
- Примеры запросов/ответов
- Требования аутентификации
- Rate limits

#### 6.1.2. API Versioning

**Требование SEC-INT-002**: API ДОЛЖНЫ использовать версионирование:

**Формат:** `/api/v1/devices`, `/api/v2/devices`

**Правила:**
- Major version изменяется при breaking changes
- Поддержка старых версий минимум 6 месяцев после релиза новой
- Deprecation warnings за 3 месяца до отключения

#### 6.1.3. API валидация

**Требование SEC-INT-003**: API Gateway ДОЛЖЕН валидировать все входящие запросы согласно OpenAPI схеме.

**Проверки:**
- ✅ Структура JSON
- ✅ Типы полей
- ✅ Обязательные поля
- ✅ Допустимые значения (enum)
- ✅ Длина строк
- ✅ Формат данных (email, UUID, ISO 8601 datetime)

**При невалидном запросе:**
- Возвращать HTTP 400 Bad Request
- Детальное описание ошибки
- НЕ обрабатывать запрос дальше

### 6.2. Направления взаимодействия

#### 6.2.1. PropDevelopment → Платформа партнера

**Требование SEC-INT-004**: PropDevelopment может вызывать следующие API партнера:

| Endpoint | Метод | Назначение | Частота |
|----------|-------|------------|---------|
| `/api/v1/devices` | GET | Получить список устройств | Раз в час |
| `/api/v1/devices/{id}/open` | POST | Открыть дверь/шлагбаум | По запросу пользователя |
| `/api/v1/devices/{id}/status` | GET | Получить статус устройства | Раз в 5 минут |
| `/api/v1/biometry/verify` | POST | Проверить биометрический шаблон | При распознавании |
| `/api/v1/guest-access` | POST | Создать гостевой доступ | По запросу пользователя |

**Требования безопасности:**
- OAuth 2.0 токен в заголовке Authorization
- mTLS для всех запросов
- Timeout: 10 секунд
- Retry: 3 попытки с exponential backoff
- Circuit breaker при ошибках

#### 6.2.2. Платформа партнера → PropDevelopment

**Требование SEC-INT-005**: Платформа партнера может вызывать следующие API PropDevelopment (через API Gateway):

| Endpoint | Метод | Назначение | Частота |
|----------|-------|------------|---------|
| `/api/v1/events` | POST | Отправить событие доступа | При каждом событии |
| `/api/v1/devices/{id}/verify-access` | POST | Проверить права доступа | Перед открытием |
| `/api/v1/biometry/match` | POST | Сопоставить биометрический шаблон с пользователем | При распознавании |

**Требования безопасности:**
- OAuth 2.0 токен от партнера
- mTLS (проверка клиентского сертификата партнера)
- Rate limiting (1000 req/min)
- IP whitelist (только известные IP адреса партнера)
- Подпись запросов (HMAC-SHA256)

#### 6.2.3. Webhooks для событий

**Требование SEC-INT-006**: Для асинхронных событий использовать Webhooks:

**События для уведомлений:**
- Дверь открыта/закрыта
- Биометрическое распознавание
- Отказ в доступе
- Устройство офлайн/онлайн
- Тревожная кнопка нажата

**Безопасность Webhooks:**
1. HTTPS endpoint на стороне PropDevelopment
2. Подпись запросов (HMAC-SHA256 с секретным ключом)
3. Проверка подписи перед обработкой
4. Идемпотентность (обработка дубликатов)
5. Retry logic с exponential backoff (3 попытки)

**Формат Webhook:**
```json
{
  "event_id": "evt_12345",
  "event_type": "door_opened",
  "timestamp": "2025-11-27T10:30:00Z",
  "device_id": "intercom_lobby_building_1",
  "user_id": "a7f3c2e1-...",
  "recognition_method": "biometric",
  "confidence": 0.98,
  "signature": "sha256=a7b2c3d4e5f6..."
}
```

### 6.3. Обработка ошибок

#### 6.3.1. Стандартизированные коды ошибок

**Требование SEC-INT-007**: API ДОЛЖНЫ использовать стандартные HTTP коды:

| Код | Значение | Когда использовать |
|-----|----------|-------------------|
| 200 | OK | Успешный запрос |
| 201 | Created | Ресурс создан |
| 400 | Bad Request | Невалидные данные |
| 401 | Unauthorized | Нет токена или токен невалидный |
| 403 | Forbidden | Токен валидный, но нет прав |
| 404 | Not Found | Ресурс не найден |
| 429 | Too Many Requests | Rate limit exceeded |
| 500 | Internal Server Error | Ошибка на сервере |
| 503 | Service Unavailable | Сервис временно недоступен |

**Формат ошибки:**
```json
{
  "error": {
    "code": "UNAUTHORIZED_ACCESS",
    "message": "User does not have permission to access this device",
    "details": {
      "user_id": "a7f3c2e1-...",
      "device_id": "intercom_123",
      "required_permission": "device:open"
    },
    "timestamp": "2025-11-27T10:30:00Z",
    "request_id": "req_xyz789"
  }
}
```

#### 6.3.2. Graceful Degradation

**Требование SEC-INT-008**: При недоступности платформы партнера система ДОЛЖНА продолжать работу в ограниченном режиме:

**Fallback механизмы:**
1. **Кеширование**: Кешировать список устройств и права доступа (TTL: 5 минут)
2. **Offline mode**: Использовать локальные правила доступа
3. **Emergency access**: Охрана может открыть дверь через альтернативный канал
4. **Уведомления**: Информировать пользователей о временных проблемах

## 7. УПРАВЛЕНИЕ ИНЦИДЕНТАМИ И РЕАГИРОВАНИЕ

### 7.1. Incident Response Plan

#### 7.1.1. Категории инцидентов

**Требование SEC-INC-001**: Определены следующие категории инцидентов для "Умного дома":

| Категория | Примеры | SLA реагирования |
|-----------|---------|------------------|
| **P0 - Critical** | - Компрометация биометрических данных<br>- Массовый несанкционированный доступ<br>- Полная недоступность системы | 15 минут |
| **P1 - High** | - Единичный несанкционированный доступ<br>- Отказ в доступе для всех пользователей<br>- Недоступность платформы партнера | 1 час |
| **P2 - Medium** | - Ошибки распознавания биометрии<br>- Отказ единичного устройства<br>- Проблемы с производительностью | 4 часа |
| **P3 - Low** | - Неточности в журнале событий<br>- UI/UX проблемы | 24 часа |

#### 7.1.2. Процедуры реагирования

**Требование SEC-INC-002**: Для инцидентов категории P0-P1 ДОЛЖНА выполняться следующая процедура:

1. **Detection** (Обнаружение): Автоматический алерт или сообщение пользователя
2. **Triage** (Классификация): Дежурный инженер определяет severity
3. **Escalation** (Эскалация): Уведомление Security Team и Management (для P0)
4. **Containment** (Изоляция): Остановка распространения инцидента
5. **Investigation** (Расследование): Анализ логов, выявление root cause
6. **Eradication** (Устранение): Исправление уязвимости
7. **Recovery** (Восстановление): Возврат в нормальный режим работы
8. **Post-Mortem** (Анализ): Документирование урок learned

#### 7.1.3. Уведомление регуляторов

**Требование SEC-INC-003**: При утечке биометрических данных ДОЛЖНО быть уведомлено:

- **Роскомнадзор**: в течение **24 часов** (ФЗ-152)
- **Затронутые пользователи**: в течение **72 часов**
- **Партнер**: немедленно

### 7.2. Аварийные процедуры

#### 7.2.1. Emergency Access

**Требование SEC-EMERGENCY-001**: Предусмотрены следующие аварийные механизмы доступа:

1. **Охрана**: Может открыть любую дверь через специальный интерфейс (требует two-factor auth)
2. **Физический ключ**: Всегда должен быть физический механизм открытия
3. **Break-glass procedure**: Экстренный доступ для пожарных/скорой (логируется)

#### 7.2.2. Kill Switch

**Требование SEC-EMERGENCY-002**: В случае критического инцидента ДОЛЖНА быть возможность:
- Отключить интеграцию с платформой партнера (одной кнопкой)
- Перевести все устройства в режим "физический ключ только"
- Заблокировать все биометрические доступы

## 8. COMPLIANCE И РЕГУЛЯТОРНЫЕ ТРЕБОВАНИЯ

### 8.1. ФЗ-152 "О персональных данных"

**Требование SEC-COMP-001**: Биометрические данные относятся к **особой категории персональных данных** (ч.1 ст.11 ФЗ-152).

#### 8.1.2. Права субъектов данных

**Требование SEC-COMP-002**: Пользователи ДОЛЖНЫ иметь возможность:

- **Право на доступ**: Посмотреть свои биометрические шаблоны (метаданные)
- **Право на исправление**: Обновить шаблон при изменении внешности
- **Право на удаление**: Удалить все биометрические данные (в течение 24 часов)
- **Право на отзыв согласия**: Отозвать согласие на обработку (деактивация биометрии)
- **Право на копию**: Получить экспорт всех своих данных

**Реализация:** Раздел "Мои данные" в мобильном приложении.

### 8.2. Аттестация и сертификация

#### 8.2.1. Аттестация информационной системы

**Требование SEC-COMP-003**: Система "Умный дом" ДОЛЖНА быть аттестована по требованиям ФСТЭК России.

**Класс защищенности:** **УЗ-1** (для систем с биометрией)

**Меры защиты:**
- Идентификация и аутентификация
- Управление доступом
- Регистрация событий
- Антивирусная защита

#### 8.2.2. Сертифицированные СКЗИ

**Требование SEC-COMP-004**: Для шифрования биометрических данных ИСПОЛЬЗОВАТЬ сертифицированные ФСБ России средства криптографической защиты.

- Шифрование биометрических шаблонов

- Semgrep

### 9.2. Функциональное тестирование безопасности

#### 9.2.1. Тест-кейсы

**Требование SEC-TEST-004**: Обязательные security test cases:

1. **Аутентификация:**
   - Попытка доступа без токена → 401
   - Попытка доступа с истекшим токеном → 401
   - Попытка доступа с чужим токеном → 403

2. **Авторизация:**
   - Собственник открывает свою дверь → Успех
   - Собственник открывает чужую дверь → 403
   - Гость с истекшим доступом → 403

3. **Защита данных:**
   - Биометрические шаблоны зашифрованы в БД → Проверка
   - API не возвращает ПД → Проверка response

4. **Rate Limiting:**
   - 11-й запрос за минуту → 429
   - После cooldown период → Успех

5. **Injection атаки:**
   - SQL Injection в параметрах → Заблокировано
   - XSS в полях ввода → Заблокировано

## 15. ЗАКЛЮЧЕНИЕ

Данный документ определяет комплексный набор требований к безопасности для интеграции систем "Умный дом" с внешней платформой партнера. 

**Ключевые принципы:**
1. 🛡️ **Defense in Depth** - многоуровневая защита
2. 🔐 **Zero Trust** - никому не доверяй, всегда проверяй
3. 🔒 **Encryption Everywhere** - шифрование везде (in transit & at rest)
4. 📝 **Logging Everything** - логирование всех событий
5. 🚨 **Proactive Monitoring** - проактивный мониторинг угроз

**Критичные компоненты:**
- **API Gateway** - единая точка входа для всех интеграций (устраняет проблему из Task2)
- **OAuth 2.0 + mTLS** - двойная аутентификация
- **Защита биометрии** - соответствие ФЗ-152 для особых категорий ПД
