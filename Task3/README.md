# Задание 3. Внешние интеграции - Умный дом

## Описание

Разработка архитектуры и требований безопасности для интеграции новых сервисов "Умный дом" от внешнего партнера:
- **Интеллектуальный домофон** с биометрическим распознаванием лиц
- **Интеллектуальный шлагбаум** с распознаванием номеров автомобилей

## Бизнес-цели

1. Расширение сервисов для собственников через существующее мобильное приложение
2. Повышение удобства и безопасности доступа в жилые комплексы
3. Автоматизация процессов управления доступом
4. Интеграция с современными технологиями (биометрия, IoT)

## Основные решения

### 1. Архитектурные решения

#### 1.1. Новый микросервис: `smart-home-integration-service`

**Назначение:** Изолированный сервис для интеграции с платформой партнера

**Функции:**
- Управление устройствами (домофон, шлагбаум)
- Обработка событий доступа
- Управление биометрическими данными (только хеши/шаблоны!)
- Правила доступа и гостевые приглашения
- Журналирование всех событий

**Обоснование изоляции:**
- Минимизация рисков (компрометация не затронет другие домены)
- Независимое масштабирование
- Упрощенный аудит и мониторинг
- Соответствие принципу separation of concerns

#### 1.2. API Gateway (КРИТИЧЕСКИЙ компонент)

**Проблема (из Task2):** Отсутствие системного контроля за API партнеров

**Решение:** Централизованный API Gateway для всех внешних интеграций

**Функции:**
- ✅ Аутентификация (OAuth 2.0)
- ✅ Авторизация (проверка прав)
- ✅ Rate Limiting (защита от DDoS)
- ✅ API Contract Validation (проверка структуры данных)
- ✅ Централизованное логирование
- ✅ Мониторинг и алертинг

**Технологии:** Kong Gateway, Apigee, AWS API Gateway

#### 1.3. Отдельная база данных: `smart-home-db`

**Содержимое:**
- Устройства и их конфигурация
- Правила доступа пользователей
- Биометрические шаблоны (зашифрованные!)
- Журнал событий (immutable)
- Гостевые доступы

**Принцип:** Никакие другие сервисы не имеют прямого доступа к этой БД

### 2. Безопасность

#### 2.1. Аутентификация: OAuth 2.0 + mTLS

**Двухуровневая аутентификация:**
1. **OAuth 2.0** (Client Credentials Grant) - machine-to-machine
   - Access token с TTL 1 час
   - Scopes для ограничения прав
   - Безопасное хранение credentials (Vault)

2. **Mutual TLS (mTLS)** - проверка сертификатов обеих сторон
   - Клиентский сертификат от PropDevelopment
   - Серверный сертификат от партнера
   - Certificate Pinning в API Gateway

**Схема:**
```
PropDevelopment → API Gateway → Партнер
     |                |             |
  OAuth 2.0        Валидация     mTLS
  (токен)          (контракт)  (сертификат)
```

#### 2.2. Защита биометрических данных (ФЗ-152)

**Особая категория персональных данных!**

**Меры защиты:**
1. ❌ **НЕ ХРАНИТЬ** исходные изображения лиц
2. ✅ **ХРАНИТЬ** только биометрические шаблоны (хеши)
3. ✅ **Шифрование** AES-256-GCM
4. ✅ **Письменное согласие** пользователя
5. ✅ **Уведомление Роскомнадзора**
6. ✅ **Сертифицированные СКЗИ** (КриптоПро CSP)

**Процесс обработки:**
```
Фото лица (устройство) 
    → Извлечение шаблона (128-512 байт)
    → Хеширование SHA-256(template || salt)
    → Шифрование AES-256(hash, key_from_HSM)
    → Хранение в smart-home-db
```

#### 2.3. Авторизация: RBAC + ABAC

**Роли (RBAC):**
- `owner` - полное управление своей квартирой
- `resident` - использование с разрешения owner
- `guest` - временный доступ
- `security` - мониторинг и экстренный доступ

**Атрибуты (ABAC):**
- `user.apartment_id` == `device.apartment_id`
- `current_time` BETWEEN `access_rule.valid_from` AND `access_rule.valid_until`
- `device.status` == `active`
- `user.biometric_consent` == `true`

#### 2.4. Логирование и мониторинг

**Логируемые события:**
- Все попытки доступа (успешные и неуспешные)
- Биометрическое распознавание
- Открытие дверей/шлагбаумов
- API вызовы (от/к партнеру)
- Изменения правил доступа
- Управление биометрией

**Алерты:**
- 🔴 Multiple failed access attempts (5 за 5 минут)
- 🔴 Biometric spoofing attempt
- 🔴 API rate limit exceeded (200%+)
- 🔴 Mass data export
- 🟠 Unusual access time (3-5 AM)

**Срок хранения:**
- События доступа: 1 год (ФЗ-152)
- Биометрические события: 3 года
- API вызовы: 6 месяцев

### 3. API интеграция

#### 3.1. PropDevelopment → Партнер

| Endpoint | Назначение |
|----------|------------|
| `GET /api/v1/devices` | Список устройств |
| `POST /api/v1/devices/{id}/open` | Открыть дверь/шлагбаум |
| `GET /api/v1/devices/{id}/status` | Статус устройства |
| `POST /api/v1/biometry/verify` | Проверка биометрии |
| `POST /api/v1/guest-access` | Создать гостевой доступ |

#### 3.2. Партнер → PropDevelopment

| Endpoint | Назначение |
|----------|------------|
| `POST /api/v1/events` | Отправка события доступа |
| `POST /api/v1/devices/{id}/verify-access` | Проверка прав |
| `POST /api/v1/biometry/match` | Сопоставление биометрии |

#### 3.3. Webhooks для событий

**Асинхронные уведомления:**
- Дверь открыта/закрыта
- Биометрическое распознавание
- Отказ в доступе
- Устройство offline/online
- Тревожная кнопка

**Безопасность Webhooks:**
- HMAC-SHA256 подпись запросов
- Проверка подписи перед обработкой
- Retry logic (3 попытки, exponential backoff)
- Идемпотентность (защита от дубликатов)

### 4. Минимизация данных (GDPR-подобный подход)

**Проблема (из Task2):** Контракты API содержат избыточные персональные данные

**Решение:** API минимизация

❌ **Плохо (слишком много ПД):**
```json
{
  "user": {
    "full_name": "Иванов Иван Иванович",
    "phone": "+79001234567",
    "address": "г. Москва, ул. Ленина, д.1, кв.42",
    "passport": "1234 567890"
  }
}
```

✅ **Хорошо (только необходимые данные):**
```json
{
  "user_id": "a7f3c2e1-4b8f-4d3a-9e2c-1a7b8c9d0e1f",
  "device_id": "device_123",
  "action": "open_door",
  "timestamp": "2025-11-27T10:30:00Z"
}
```
