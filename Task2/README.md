# Задание 2. Проверочный лист безопасности для бизнес-систем PropDevelopment

## Анализ систем и выбор разделов

### Идентифицированные системы

#### Домен: Группа сервисов для продаж

## Выбор разделов проверочного листа

На основе выявленных проблем компании (см. Task1) выбраны следующие приоритетные разделы:

### 1. Аутентификация и авторизация (КРИТИЧЕСКИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🔴 **Критическая проблема**: клиенты видят данные других клиентов в личном кабинете
- 🔴 Партнеры могут получать доступ к данным других управляющих компаний
- 🔴 Отсутствует централизованная система управления доступом
- Необходимо проверить механизмы аутентификации во всех системах
- Важно убедиться в корректной изоляции данных между пользователями

**Ключевые вопросы:**
- Используется ли многофакторная аутентификация?
- Как реализована изоляция данных пользователей?
- Есть ли централизованная система IAM?
- Как контролируется доступ к API?

### 2. Управление доступом (КРИТИЧЕСКИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🔴 Несколько точек регистрации клиента без координации
- 🔴 Отсутствие системного контроля за передаваемыми данными
- 🔴 Нет ограничений на доступ к данным между доменами
- Требуется проверка механизмов RBAC (Role-Based Access Control)
- Необходимо убедиться в наличии принципа наименьших привилегий

**Ключевые вопросы:**
- Реализован ли принцип наименьших привилегий?
- Как управляются роли и права доступа?
- Есть ли разделение обязанностей (Separation of Duties)?
- Как контролируется доступ к базам данных?

### 3. Защита данных (КРИТИЧЕСКИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🔴 Работа с персональными данными клиентов и собственников (ФЗ-152)
- 🔴 Обработка платежных данных (требования PCI DSS)
- 🔴 Финансовая отчетность компании (коммерческая тайна)
- 🔴 Данные для онлайн-сделок (юридическая значимость)
- Необходимо соответствие требованиям законодательства РФ

**Ключевые вопросы:**
- Шифруются ли данные при передаче (TLS/SSL)?
- Шифруются ли данные при хранении?
- Как классифицируются данные?
- Применяется ли маскирование/анонимизация данных?

### 4. Безопасность API (ВЫСОКИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🔴 **Критическая проблема**: отсутствие единых политик безопасности для API партнеров
- 🔴 Контракты API содержат персональные данные
- 🔴 Нет системного контроля за передаваемыми данными через API
- Множество интеграций: госорганы, платежные системы, управляющие компании
- Планируется расширение партнерских сервисов

**Ключевые вопросы:**
- Есть ли API Gateway с контролем безопасности?
- Как осуществляется аутентификация API (API keys, OAuth2, JWT)?
- Применяются ли rate limiting и throttling?
- Как контролируется состав данных в API-контрактах?

### 5. Логирование и мониторинг (ВЫСОКИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🟡 Необходимость выявления инцидентов безопасности (отображение чужих данных)
- 🟡 Требование аудита доступа к персональным данным (ФЗ-152)
- 🟡 Необходимость расследования инцидентов
- 🟡 Конкуренты столкнулись с утечкой данных - нужен проактивный мониторинг

**Ключевые вопросы:**
- Логируются ли события безопасности?
- Есть ли централизованная система сбора логов?
- Настроены ли алерты на подозрительную активность?
- Как долго хранятся логи?

### 6. Управление инцидентами ИБ (ВЫСОКИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🟡 Зафиксированы инциденты с отображением чужих данных
- 🟡 Один специалист по ИБ на всю компанию (недостаточно ресурсов)
- 🟡 Нарушен процесс передачи информации между командами
- 🟡 Необходимость быстрого реагирования на инциденты

**Ключевые вопросы:**
- Есть ли процесс управления инцидентами ИБ?
- Кто отвечает за реагирование на инциденты?
- Есть ли план реагирования на инциденты (IRP)?
- Как информируются заинтересованные стороны?

### 7. Защита сети (СРЕДНИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🟢 Есть межсетевой экран для внешних пользователей
- 🟡 Необходима проверка сегментации сети между доменами
- 🟡 Множество интеграций с внешними системами
- 🟡 Гибридная инфраструктура (собственный ЦОД + облако)

**Ключевые вопросы:**
- Настроена ли сегментация сети?
- Как защищены внутренние коммуникации между сервисами?
- Применяется ли DDoS-защита?
- Как контролируется сетевой трафик?

### 8. Резервное копирование и восстановление (СРЕДНИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🟢 Уже выполняется резервное копирование баз данных
- 🟡 Необходимо проверить полноту и регулярность
- 🟡 Критичность данных для бизнеса (сделки, платежи)
- 🟡 Требования по времени восстановления (RTO/RPO)

**Ключевые вопросы:**
- Какие данные включены в резервное копирование?
- Как часто выполняется копирование?
- Тестируется ли процесс восстановления?
- Где хранятся резервные копии?

### 9. Управление уязвимостями (СРЕДНИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🟡 Активное развитие IT-ландшафта (новые интеграции)
- 🟡 Недавние изменения в руководстве IT-команд
- 🟡 Необходимость проактивного выявления уязвимостей
- 🟡 Риск эксплуатации уязвимостей злоумышленниками

**Ключевые вопросы:**
- Проводится ли сканирование на уязвимости?
- Как часто обновляется ПО и зависимости?
- Есть ли процесс Patch Management?
- Проводятся ли пентесты?

### 10. Безопасность разработки (СРЕДНИЙ ПРИОРИТЕТ)

**Обоснование:**
- 🟡 Выявлены архитектурные проблемы безопасности
- 🟡 Необходимость внедрения Security by Design
- 🟡 Активная разработка новых сервисов (BI, ML, AI)
- 🟡 Недостаточное вовлечение специалиста по ИБ

**Ключевые вопросы:**
- Проводится ли код-ревью с точки зрения безопасности?
- Используются ли инструменты SAST/DAST?
- Вовлечен ли специалист по ИБ на этапе проектирования?
- Есть ли процесс Security Champions?

## Приоритизация проверок

### Критические (немедленное исполнение):
1. Аутентификация и авторизация
2. Управление доступом
3. Защита данных
4. Безопасность API

### Высокие (в течение месяца):
5. Логирование и мониторинг
6. Управление инцидентами ИБ

### Средние (в течение квартала):
7. Защита сети
8. Резервное копирование и восстановление
9. Управление уязвимостями
10. Безопасность разработки

## Методология проверки

Для каждой системы в проверочном листе указываются:

1. **Название системы** - идентификатор системы
2. **Домен** - к какому бизнес-домену относится
3. **Критичность** - оценка важности для бизнеса (Критическая/Высокая/Средняя/Низкая)
4. **Раздел проверки** - какой аспект безопасности проверяется
5. **Проверяемый параметр** - конкретный вопрос или требование
6. **Ожидаемое состояние** - какой результат считается соответствующим требованиям
7. **Текущее состояние** - фактическое состояние (если известно из описания)
8. **Статус** - результат проверки (Соответствует/Не соответствует/Требует проверки/Не применимо)
9. **Риск** - уровень риска при несоответствии (Критический/Высокий/Средний/Низкий)
10. **Рекомендации** - предлагаемые меры по устранению проблемы

## Следующие шаги

После заполнения проверочного листа необходимо:

1. Провести фактический аудит каждой системы
2. Обновить статусы на основе результатов проверки
3. Приоритизировать выявленные проблемы
4. Разработать план устранения несоответствий
5. Назначить ответственных за реализацию мер
6. Установить сроки исполнения
7. Организовать регулярный мониторинг выполнения плана
