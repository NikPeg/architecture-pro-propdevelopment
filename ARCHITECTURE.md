# Архитектура PropDevelopment - Диаграмма контейнеров C4

## Обзор

Данный документ содержит детальное описание архитектуры IT-систем компании PropDevelopment на уровне контейнеров (Container Diagram) согласно нотации C4.

## Внешние актеры

### Пользовательские роли (слева)

1. **Клиент** — человек, покупающий квартиру
   - Взаимодействует с Витриной продаж через Гейт
   
2. **Менеджер** — обрабатывает заявки клиентов и общается с ними
   - Работает напрямую с client-crm-app
   
3. **Бизнес-аналитик** — проводит анализ данных для поддержки принятия решений
   - Использует систему отчетности и BI

4. **Бухгалтер** — ведет бухгалтерский учет
   - Работает с accountant-service-1

### Пользовательские роли (справа)

5. **Собственник** — владелец квартиры
   - Взаимодействует с Витриной сервисов для собственников через Гейт

6. **Audience BI** — сотрудники компании и владельцы бизнеса
   - Получают аналитические данные из хранилища по JDBC

### Внешние системы

7. **Государственные регистрационные органы** (Росреестр и другие)
   - Интеграция с доменом продаж для проведения онлайн-сделок
   
8. **Платежные системы** (MasterCard, Visa, Мир)
   - Интеграция с сервисами ЖКУ для оплаты услуг
   
9. **Поставщики ресурсов ЖКХ** (Теплосети, Водоканал и другие)
   - Интеграция с доменом ЖКУ

## Домен 1: Группа сервисов для продаж

### Точка входа

**Витрина продаж** (клиентский портал)
- Назначение: позволяет клиентам просматривать и бронировать недвижимость
- Тип: Веб-приложение (монолит)
- Пользователи: Клиенты (через Гейт)

### Приложения и сервисы

#### 1. client-mart-estate-app
- **Назначение**: управление портфелем недвижимости
- **База данных**: client-mart-estate-db
- **Описание**: хранит информацию о доступных объектах недвижимости, планировках, ценах
- **Протоколы взаимодействия**: HTTP, gRPC

#### 2. client-mart-app
- **Назначение**: онлайн-сделка (оформление покупки недвижимости)
- **База данных**: client-mart-db
- **Описание**: обеспечивает процесс проведения сделки купли-продажи недвижимости онлайн
- **Интеграции**: 
  - client-tour-db (по gRPC)
  - Государственные регистрационные органы
- **Протоколы взаимодействия**: HTTP, gRPC, ODBC

#### 3. client-tour-app
- **Назначение**: онлайн-тур (виртуальный осмотр недвижимости)
- **База данных**: client-tour-db
- **Описание**: позволяет клиентам проводить виртуальные осмотры объектов недвижимости
- **Протоколы взаимодействия**: HTTP, gRPC

#### 4. client-crm-app
- **Назначение**: система управления клиентами (CRM)
- **База данных**: crm-db
- **Описание**: управление данными о клиентах, их заявках и истории взаимодействий
- **Пользователи**: Менеджеры
- **Протоколы взаимодействия**: HTTP, LDAP

### Особенности взаимодействия

- Все сервисы взаимодействуют между собой по HTTP и gRPC
- Витрина продаж запрашивает данные из всех backend-сервисов
- client-crm-app напрямую доступен менеджерам для работы с клиентами
- Данные передаются в Хранилище данных по протоколу JDBC

## Домен 2: Группа сервисов ЖКУ

### Точка входа

**Витрина сервисов для собственников**
- Назначение: мобильное приложение для взаимодействия с управляющей компанией
- Тип: Мобильное приложение
- Пользователи: Собственники (через Гейт)
- **Группа сервисов**: Онлайн-сервисы для ЖКУ

### Приложения и сервисы

#### 1. tenant-core-app
- **Назначение**: предоставление услуг собственникам (управление ЖКУ)
- **База данных**: tenant-core-db
- **Описание**: ядро системы для управления жилищно-коммунальными услугами
- **Функциональность**:
  - Оплата услуг ЖКХ
  - Информация от управляющей компании
  - Мониторинг ремонтов
  - Управление "Умным домом"
- **Интеграции**:
  - Платежные системы (МХ - MasterCard, Visa, Мир)
  - Поставщики ресурсов ЖКХ
  - auth-service-1 (по LDAP)
- **Протоколы взаимодействия**: HTTP, gRPC, LDAP, JDBC

#### 2. CRM (tenant Suite SaaS)
- **Назначение**: система управления данными собственников
- **База данных**: tenant-estate-crm-db
- **Описание**: управление информацией о собственниках, их квартирах и взаимодействиях
- **Протоколы взаимодействия**: HTTP, LDAP, JDBC

### Особенности взаимодействия

- Витрина сервисов взаимодействует с tenant-core-app по HTTP и gRPC
- tenant-core-app интегрируется с внешними платежными системами
- Все данные передаются в Хранилище данных по JDBC
- Связь с auth-service-1 для авторизации по LDAP

## Домен 3: Финансы

### Приложения и сервисы

#### 1. accountant-service-1
- **Назначение**: система финансового учёта
- **База данных**: auth-db-1 (хранилище финансовых данных)
- **Описание**: ведение бухгалтерского и финансового учета компании
- **Пользователи**: Бухгалтер
- **Протоколы взаимодействия**: HTTP, LDAP, JDBC

#### 2. Active Directory
- **Назначение**: каталог для пользователей (аутентификация сотрудников)
- **Описание**: централизованная служба управления пользователями и правами доступа
- **Протоколы взаимодействия**: LDAP

### Особенности взаимодействия

- Бухгалтер работает с accountant-service-1 напрямую
- Active Directory используется для аутентификации сотрудников во всех системах
- Связь с внешними системами по протоколу LDAP
- Финансовые данные передаются в Хранилище по JDBC

## Домен 4: Дата (обработка данных)

### Приложения и сервисы

#### 1. Хранилище данных (DWH-1-warehouse)
- **Назначение**: аналитическое хранилище данных
- **База данных**: DWH-1-warehouse
- **Описание**: централизованное хранилище для всех данных компании
- **Источники данных**:
  - Все сервисы домена продаж (по JDBC)
  - Все сервисы домена ЖКУ (по JDBC)
  - Финансовый домен (по JDBC)
- **Потребители**: Audience BI (по JDBC)
- **Протоколы взаимодействия**: JDBC

#### 2. auth-service-1
- **Назначение**: служба авторизации и аутентификации
- **База данных**: auth-db-1
- **Описание**: централизованная система управления доступом
- **Интеграции**:
  - auth-service-1 (хранилище финансовых данных)
  - tenant-core-app (авторизация собственников)
  - Active Directory (LDAP)
- **Протоколы взаимодействия**: LDAP, HTTP

### Особенности взаимодействия

- Все домены передают данные в Хранилище по JDBC
- Хранилище является единым источником данных для аналитики
- auth-service-1 интегрируется с различными доменами для контроля доступа

## Протоколы взаимодействия

В архитектуре используются следующие протоколы:

1. **HTTP/HTTPS** — основной протокол для взаимодействия между веб-приложениями и сервисами
2. **gRPC** — для высокопроизводительного взаимодействия между микросервисами
3. **LDAP** — для аутентификации и работы с Active Directory
4. **JDBC** — для передачи данных в хранилище и доступа к базам данных
5. **ODBC** — для специфичных интеграций с внешними системами

## Точки входа (Gateway/Firewall)

### Гейт для клиентов
- Обеспечивает доступ клиентов к Витрине продаж
- Проходит через межсетевой экран (firewall)

### Гейт для собственников
- Обеспечивает доступ собственников к Витрине сервисов ЖКУ
- Проходит через межсетевой экран (firewall)

## Внешние интеграции

### 1. Государственные регистрационные органы
- **Назначение**: проведение онлайн-сделок
- **Взаимодействие**: с доменом продаж (client-mart-app)
- **Данные**: регистрация прав собственности, проверка документов

### 2. Платежные системы
- **Назначение**: обработка платежей за ЖКУ
- **Взаимодействие**: с доменом ЖКУ (tenant-core-app)
- **Системы**: MasterCard, Visa, Мир и другие

### 3. Поставщики ресурсов ЖКХ
- **Назначение**: получение данных о потреблении ресурсов
- **Взаимодействие**: с доменом ЖКУ (tenant-core-app)
- **Поставщики**: Теплосети, Водоканал и другие

### 4. Платежные системы сторонних производителей (MХ Rх)
- **Назначение**: альтернативные способы оплаты
- **Взаимодействие**: с доменом ЖКУ

## Проблемы архитектуры (выявленные)

### Критические проблемы безопасности

1. **Отсутствие централизованного контроля доступа**
   - Множественные точки регистрации клиентов без координации
   - Клиенты могут видеть данные других клиентов

2. **Несистемный контроль потоков данных**
   - Отсутствуют ограничения на доступ к данным между доменами
   - Нет единой политики безопасности для API

3. **Проблемы с партнерскими API**
   - Контракты API содержат персональные данные
   - Партнеры могут получать доступ к данным других управляющих компаний

4. **Недостаточная изоляция данных**
   - Прямой доступ к базам данных по JDBC из множества точек
   - Отсутствие единого слоя контроля доступа к данным

5. **Информационная безопасность**
   - Один специалист по ИБ на всю компанию
   - Нарушен процесс передачи информации о изменениях

### Рекомендации по улучшению

1. Внедрить **API Gateway** для всех внешних интеграций
2. Реализовать **централизованную систему IAM** (Identity and Access Management)
3. Создать **единую точку регистрации** клиентов (Master Data Management)
4. Внедрить **Data Loss Prevention (DLP)** систему
5. Реализовать **микросервисную архитектуру** для лучшей изоляции доменов
6. Добавить **Service Mesh** для контроля межсервисного взаимодействия
7. Внедрить **систему мониторинга и аудита** доступа к данным
8. Усилить команду информационной безопасности
